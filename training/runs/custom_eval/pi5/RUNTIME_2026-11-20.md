# Pi 5: ONNX vs NCNN heads, body re-ID cost, the demo room's detector alarms (2026-11-20)

Raspberry Pi 5 8 GB (the team's demo unit), Raspberry Pi OS Trixie, Python
3.13.5, onnxruntime 1.31.0, OpenCV 4.14.0; SENTRIX at `66e4a4c` (GitHub `main`).
The heads are the Pi's own: person `yolov8n`, weapon `v5_room`, fire
`v4_custom` (pinned by `SENTRIX_FIRE_WEIGHTS`, owner 2026-11-19), all at 320 px
with 4 threads. Frames: train + val videos `gun`, `vid04`, `mmgun`, `mmknife`,
`vid07`, `nvroom2`, `vid06`, resized to 1280 x 720 (the camera's size); `wa02`
is never read. Scripts: `pi_runtime_parity.py`, `pi_reid_cost.py` (run on the
Pi from `~/Sentrix` with the script on stdin; they write nothing). ncnn
1.0.20261020 and the three NCNN exports were installed for this test and
removed afterwards.

## Agreement with ONNX (102 frames, service running)

scores >= 0.1), the top score per label at 0.25, and the frames whose set of

|---|---|---|---|---|---|
| person | defaults (fp16) | 0.034 / 0.377 | 0.054 | 280 / 275 | 4 / 6 / 2 |
| person | fp32 | 0.000 / 0.000 | 0.000 | 280 / 280 | 0 / 0 / 0 |
| weapon | defaults (fp16) | 0.010 / 0.013 | 0.008 | 5 / 4 | 1 / 0 / 0 |
| weapon | fp32 | 0.000 / 0.000 | 0.000 | 5 / 5 | 0 / 0 / 0 |
| fire | defaults (fp16) | 0.005 / 0.011 | 0.006 | 5 / 5 | 0 / 0 / 0 |
| fire | fp32 | 0.000 / 0.000 | 0.000 | 5 / 5 | 0 / 0 / 0 |

A first run of the person head alone on 207 frames (defaults) gave 13 / 5 / 2
differing frames. On the x86 laptop (no fp16 arithmetic) the same NCNN exports
agree with ONNX within 1e-5 (`tools/export_models.py`), so the difference shows
only on the Pi.

**Decision: the Pi stays on ONNX.** NCNN is about twice as fast only with
ncnn's fp16 arithmetic, which changes the person head's decisions on 4-6 % of
frames; the person head gates weapon evidence (a weapon needs a person seen in
the last 2 s) and the room calibration (D23) rebuilds that gate from logged
boxes, and every replay and calibration of the Pi configuration was made on
ONNX. With fp32 arithmetic NCNN equals ONNX and is no faster. What fp16 would
have bought: about 56 ms per keyframe for the three heads, about 0.3 s of the
3.9 s clip compute (`REPORT.md`), where the scene model's 2.4 s dominates.

The same request exercised the Portal's offline rule: the Render Portal was
still waking from suspension (HTTP 503/500 on the link until 19:26), the link
then reconnected about once a minute, the Portal marked the device offline at
19:27:09 with the request PENDING and queued the contact's alert (`contacts_t0`,
Telegram), which failed (`ReadTimeout`); the contact's "resolved" message
failed every 2 minutes (`ReadTimeout`, once `502 Bad Gateway`) until it was
delivered at 14:34 UTC (20:04 IST), about 40 minutes after the Portal woke up.
The link's reconnects eased at the same time (every ~70 s until 20:01, then
two between 20:01 and 20:15). Telegram's API answered normally from India
throughout (`curl https://api.telegram.org`, 302 in 0.6-1.5 s), so the fault
was on Render's side right after the resume. The owner's e-mails were
suppressed (`SENTRIX_EMAIL_LIVE` off).

What the code did wrong in that window, fixed in `2c900c1`: the device logged no
reason for a dropped session; its back-off reset only after 60 s connected,
so a drop soon after the wake-up kept it away past the Portal's 45 s offline
limit (hence the contact's page); the decline sent the contact "resolved by
the resident" for an alert that never arrived; every failing retry was
mirrored to the device; a failing Telegram poll was silent.
